# Adversarial verification: projects, firmware and host tooling

Audit date: **24 October 2026**. This independently challenges [the project survey](research.md) and [the firmware-analysis report](firmware-analysis-research.md). It distinguishes agreement with an upstream source from independent reproduction of the upstream software.

## Verdict

The central distinction survives scrutiny: modern graphical iOS research guests, barebones Darwin kernel environments, historical hardware emulators and app-level compatibility projects are different implementation paths. The research is useful for selecting experiments. It does **not** establish that this repository can boot current retail iOS, that a Go host port is already viable, or that a firmware-derived hardware contract has been validated.

Two current-source statements need correction: S5LBox is already released, and GhidrAssistMCP's current prerequisites no longer advertise Ghidra 11.4+. The larger weakness is evidence provenance and the gap between documented capabilities and reproduced behavior.

## Findings requiring correction or qualification

### 1. Contradicted: S5LBox is preparing for its first release

The original survey's S5LBox paragraph says it is preparing for its first release. The current README provides an IPA download and setup flow. The release page lists **1.1.0, released 19 October 2026**. Replace the first-release claim with that release evidence. This does not independently validate the emulator's graphical, networking or app-installation claims. [Current README](https://github.com/j0shua-SYSON/S5LBox/blob/main/README.md), [published releases](https://github.com/j0shua-SYSON/S5LBox/releases)

The warning about stale architecture material remains warranted: the architecture document retains an opening diagram with absent input/audio and later records graphical validation. Treat each validation result as attached to its named commit and scenario; do not combine historical sections into one current feature matrix. [Architecture and validation notes](https://github.com/j0shua-SYSON/S5LBox/blob/main/docs/ARCHITECTURE.md)

### 2. Contradicted: current GhidrAssistMCP guidance supports Ghidra 11.4+

The firmware report's integration table gives an 11.4+ baseline. The current prerequisites specify **Ghidra 12.0 or 12.1 Public, Java 25 or newer**, and extension ZIPs specific to the selected Ghidra version. Update the row. Its advertised native Java server, multiple programs, asynchronous tasks and SSE/Streamable HTTP architecture are supported by current documentation; their operational correctness was not tested. [Current prerequisites and architecture](https://github.com/symgraph/GhidrAssistMCP#installation)

### 3. Unverifiable historical provenance: the original PMV digest

The original report records a 76,529-byte PMV response and a digest but explicitly says the response bytes were not retained. A fresh audit retrieval was also 76,529 bytes and matched the reported target/build/date rows, but its SHA-256 was **`ac36c4037bf31603320b1450b8caf4cf7793ef47da7ccbbf5a6968405b971750`**, differing from the original digest. A changing response or serialization can explain different bytes. The difference neither authenticates nor disproves the historical snapshot. It makes that exact historical digest unreproducible from repository evidence.

The audit now retains a [fresh raw PMV response](research-artifacts/verification/pmv-response.json), [metadata summary with capture times and digests](research-artifacts/verification/metadata-verification.json), and [CDN response headers](research-artifacts/verification/apple-cdn-head.txt). These are new observations, not a replacement masquerading as the original capture. [Apple PMV endpoint](https://gdmf.apple.com/v2/pmv)

### 4. Important limitation: no implementation evidence establishes stock-device fidelity

The report generally labels project claims honestly, but the future project's hypothesis must remain narrower than “reverse engineering the newest IPSW tells us how an iPhone VM works.” vphone's working recipe combines iPhone userspace and cloudOS virtual-platform components with patches; darwin-vm uses a recovery-style filesystem and lacks graphical hardware. A successful run of either is evidence about that constructed environment. It does not demonstrate equivalence to an unmodified physical phone or completeness of a retail hardware model. [vphone compatibility and patch requirements](https://github.com/Lakr233/vphone-cli/blob/main/Documents/Guides/compatibility.md), [darwin-vm scope and limitations](https://github.com/jprx/darwin-vm#what-this-is-not)

## Scope that remains unverified

This audit read both documents in full and revisited the consequential sources above. It did not independently recheck every minor feature, historical date, license file, wrapper repository or auxiliary link. It did not build the surveyed emulators, run a Go binding, import firmware into Ghidra, install MCP, request restore authorization, download firmware payloads or boot a VM.

Apple's PCC architecture/setup URLs returned JavaScript document shells through the browsing interface; ordinary HTML retrieval did not expose their substantive content. Therefore this audit does not newly certify each VRE prerequisite or the exact current research-use terms. The original document's citations remain leads to inspect in a reader that exposes the content, not grounds for claiming those details were independently reconfirmed here. [VRE architecture](https://security.apple.com/documentation/private-cloud-compute/virtualresearchenvironment), [VRE setup](https://security.apple.com/documentation/private-cloud-compute/vresetup)

Mutable main/master URLs are suitable reading links but weak historical evidence. Before implementation, pin the chosen engine, its submodules, patch recipe and exact firmware component hashes. The decisive next result is one repeated, trace-backed contract on an exact working guest, including a deliberately failing case. Until that exists, the firmware workflow remains a credible research proposal rather than a validated implementation specification.
